# ADR-001. Выбор эндпоинта TronScan и модель идемпотентности

**Статус:** принято
**Дата:** 2026-08-04
**Контекст:** сервис учёта входящих USDT TRC-20 депозитов, read-only интеграция с explorer API.

---

## 1. Какой эндпоинт используем

```http
GET https://apilist.tronscanapi.com/api/token_trc20/transfers
  ?relatedAddress={wallet}
  &contract_address=TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t
  &limit=50&start=0
Header: TRON-PRO-API-KEY: {key}
```

### Почему он

* Фильтрация **по контракту на стороне API**: не нужно тянуть весь трафик кошелька и отсеивать чужие
  токены локально. Для «десков», где адрес принимает только USDT, это самый дешёвый по трафику вариант.
* Ответ уже содержит всё для маппинга в `deposits`: `transaction_id`, `from_address`, `to_address`,
  `quant` (единицы токена), `tokenInfo.tokenDecimal`, `block_ts` (мс), `contract_ret`/`confirmed`.
* Пагинация `limit` + `start` и поле `total` — предсказуемая и легко тестируемая.

### Альтернативы

| Вариант | Почему не выбран |
|---------|------------------|
| `/api/transfer/list` (общий список трансферов) | не фильтрует по TRC-20 контракту так же прямо — больше лишних данных и разбора на нашей стороне |
| `/api/account/tokens` (балансы) | даёт только текущий баланс, а нужна **история отдельных переводов** с tx hash |
| Полная нода TRON / TronGrid `getTransactionsToAddress` | требует парсинга событий контракта и hex-адресов; для теста избыточно, дороже в поддержке |

Смена эндпоинта локализована: URL — в `config/tronscan.php`, разбор ответа — в `Trc20Transfer::fromApi()`,
запрос — в `TronScanHttpClient`. `TronScanHttpClient` дополнительно понимает ключ `data` вместо
`token_transfers` — на случай альтернативного эндпоинта.

---

## 2. Направление перевода

`relatedAddress` возвращает трансферы **в обе стороны**. Депозитом считаем только
`to_address == wallet.address` (строгое сравнение base58). Исходящие учитываются как `skipped`
и попадают в `sync_runs.fetched_count`, но не в `created_count`.

---

## 3. Идемпотентность

Три уровня, от дешёвого к надёжному:

1. **Проверка перед вставкой** — `deposits.where('tx_hash', ...)->exists()`. Отсекает 99% повторов
   при последовательных прогонах, стоит один индексный lookup.
2. **Unique-индекс `deposits.tx_hash`** — единственная настоящая гарантия. При гонке двух воркеров
   (ручной «Sync now» + расписание) `UniqueConstraintViolationException` перехватывается
   в `DepositSyncService::store()` и трансфер считается пропущенным, а не ошибкой прогона.
3. **`SyncWalletDepositsJob implements ShouldBeUnique`** (`uniqueFor = 600`) — два прогона по одному
   кошельку не стартуют параллельно, гонка из п.2 остаётся страховкой, а не рабочим сценарием.

Почему ключ именно `tx_hash`, а не `(wallet_id, tx_hash)`: этого требует задание, и для USDT-переводов
одна транзакция = один интересующий нас перевод на адрес. Компромисс: если в одной транзакции
несколько переводов на **разные** наши кошельки, сохранится только первый. Это осознанное ограничение;
при необходимости расширяется до unique `(tx_hash, to_address)` без изменения логики сервиса.

## 4. Деньги

`quant` приходит в базовых единицах (`12500000` при 6 decimals). Конвертация — посимвольный сдвиг
десятичной точки в `TokenAmount::fromBaseUnits()`:

* нет `float` нигде в цепочке API → БД → API;
* не нужен `ext-bcmath` (в Docker он всё же ставится — пригодится дальше);
* в БД `decimal(36,6)`, в PHP — строка (`'amount' => 'decimal:6'`);
* decimals берём из ответа (`tokenInfo.tokenDecimal`), а не из константы, с фолбэком на конфиг.

## 5. Ошибки и ретраи

| Ситуация | Исключение | Ретрай |
|----------|------------|--------|
| Сетевой сбой / таймаут | `TronScanServerException` | да |
| 429 (rate limit — типично без API-ключа) | `TronScanRateLimitException` | да |
| 5xx | `TronScanServerException` | да |
| 4xx (битый адрес, неверный ключ) | `TronScanRequestException` | нет |
| 2xx с неожиданной структурой | `TronScanResponseException` | нет |

Ретраи — на уровне HTTP-клиента (`retry_times`, `retry_sleep_ms`), повторная постановка задачи —
на уровне очереди (`tries = 3`, `backoff = [10, 30, 60]`). Любой исход прогона фиксируется
в `sync_runs` (`status`, `error_message`, `started_at`, `finished_at`), поэтому диагностика
не требует чтения логов контейнера.

## 6. Драйвер `fake`

Проверяющий не должен заводить API-ключ, чтобы увидеть работающий продукт, а CI не должен ходить в сеть.
Поэтому контракт `TronScanClient` имеет вторую реализацию `FakeTronScanClient`, читающую фикстуру
`database/fixtures/tronscan/token_trc20_transfers.json`; выбор — через `TRONSCAN_DRIVER`.
Фикстура одна и та же для демо и тестов, так что «демо-режим» проверяется теми же ассертами,
что и боевой маппинг.
